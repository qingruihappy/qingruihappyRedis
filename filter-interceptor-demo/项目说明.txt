项目概述
─────────────────────────────────────────────────────────────────────────────
本项目完整演示了 Spring MVC 中 Filter 和 Interceptor 的执行流程，
包括正常流程和异常处理的各种场景，帮助理解两者的区别和使用场景。


核心功能
─────────────────────────────────────────────────────────────────────────────
✓ 三个 Filter（FirstFilter、SecondFilter、ThirdFilter）
✓ 三个 Interceptor（FirstInterceptor、SecondInterceptor、ThirdInterceptor）
✓ 一个测试 Controller
✓ 异常场景控制（通过请求参数）
✓ 详细的日志输出
✓ 完整的时序图

关键知识点
─────────────────────────────────────────────────────────────────────────────

Filter vs Interceptor
┌────────────────┬─────────────────────┬─────────────────────────┐
│     维度       │       Filter        │      Interceptor        │
├────────────────┼─────────────────────┼─────────────────────────┤
│ 级别           │ Servlet容器级别     │ Spring MVC级别          │
│ 依赖           │ Servlet API         │ Spring框架              │
│ 执行位置       │ DispatcherServlet前 │ DispatcherServlet内     │
│ 异常处理       │ 需要显式catch       │ Spring自动处理          │
│ 访问Spring Bean│ 不方便              │ 可以直接注入            │
│ 后置执行保证   │ try-finally才保证   │ afterCompletion总执行   │
└────────────────┴─────────────────────┴─────────────────────────┘

执行顺序记忆
┌─────────────────────────────────────────────────────────────────┐
│ Filter 执行顺序:                                                 │
│   前置: 按 Order 顺序 (1 → 2 → 3)                               │
│   后置: 倒序执行 (3 → 2 → 1)                                    │
│   模型: 洋葱模型（一层包一层）                                   │
│                                                                  │
│ Interceptor 执行顺序:                                            │
│   preHandle:       按注册顺序 (1 → 2 → 3)                       │
│   postHandle:      倒序执行 (3 → 2 → 1)                         │
│   afterCompletion: 倒序执行 (3 → 2 → 1)                         │
│   特点: 只有执行了 preHandle 的才会调用 afterCompletion         │
└─────────────────────────────────────────────────────────────────┘

异常处理机制
┌─────────────────────────────────────────────────────────────────┐
│ Filter 异常:                                                     │
│   ✗ 如果不捕获，整个请求链中断                                   │
│   ✓ 捕获后可以自定义错误响应                                     │
│   ✗ 后续所有组件都不会执行                                       │
│                                                                  │
│ Interceptor 异常:                                                │
│   ✓ Spring 自动处理，不需要显式捕获                              │
│   ✓ afterCompletion 会执行（对于已执行 preHandle 的）           │
│   ✓ Filter 后置处理仍然执行                                      │
│   ✗ postHandle 不会执行                                          │
└─────────────────────────────────────────────────────────────────┘


DispatcherServlet 的角色
─────────────────────────────────────────────────────────────────────────────
DispatcherServlet 是 Spring MVC 的核心组件，它的作用：

1. 接收请求（从 Filter 链传递过来）
2. 查找 Handler（Controller 方法）
3. 调用 Interceptor 的 preHandle
4. 执行 Handler（Controller 方法）
5. 调用 Interceptor 的 postHandle
6. 处理视图渲染
7. 调用 Interceptor 的 afterCompletion
8. 返回响应（给 Filter 链）

它是连接 Filter 和 Interceptor 的桥梁！

常见问题 FAQ
─────────────────────────────────────────────────────────────────────────────

Q1: 为什么 Filter 异常时，FirstFilter 的后置处理不执行？
A1: 因为异常在 catch 块中被捕获，try 块后面的代码不会执行。
    如果需要后置处理总是执行，应该使用 try-finally 结构。

Q2: 为什么 Interceptor 异常时，Filter 的后置处理还会执行？
A2: Filter 采用洋葱模型，即使 DispatcherServlet 内部抛异常，
    只要异常被处理了（不向外抛），Filter 的后置代码仍会执行。

Q3: 为什么只有 FirstInterceptor 的 afterCompletion 执行？
A3: 这是 Spring 的设计：只有成功执行 preHandle 的拦截器，
    其 afterCompletion 才会被调用。这保证了资源准备和清理的对称性。

Q4: 生产环境中如何选择 Filter 还是 Interceptor？
A4: Filter: 通用的请求处理（编码、跨域、安全），不依赖 Spring
    Interceptor: 业务相关处理（权限、日志），需要访问 Spring Bean
