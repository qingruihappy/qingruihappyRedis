## 二、详细执行流程对比

### 场景1: 正常流程（无异常）

```
时间线    组件                      动作                      状态
───────┼────────────────────┼───────────────────────┼─────────
  1    │ FirstFilter        │ 前置处理               │ ✓
  2    │ SecondFilter       │ 前置处理               │ ✓
  3    │ ThirdFilter        │ 前置处理               │ ✓
  4    │ DispatcherServlet  │ 接收请求，查找Handler   │ ✓
  5    │ FirstInterceptor   │ preHandle()            │ ✓ 返回true
  6    │ SecondInterceptor  │ preHandle()            │ ✓ 返回true
  7    │ ThirdInterceptor   │ preHandle()            │ ✓ 返回true
  8    │ Controller         │ 处理业务逻辑           │ ✓
  9    │ ThirdInterceptor   │ postHandle()           │ ✓ 倒序
 10    │ SecondInterceptor  │ postHandle()           │ ✓ 倒序
 11    │ FirstInterceptor   │ postHandle()           │ ✓ 倒序
 12    │ ThirdInterceptor   │ afterCompletion(null)  │ ✓ 倒序
 13    │ SecondInterceptor  │ afterCompletion(null)  │ ✓ 倒序
 14    │ FirstInterceptor   │ afterCompletion(null)  │ ✓ 倒序
 15    │ ThirdFilter        │ 后置处理               │ ✓ 倒序
 16    │ SecondFilter       │ 后置处理               │ ✓ 倒序
 17    │ FirstFilter        │ 后置处理               │ ✓ 倒序
 18    │ 客户端             │ 收到响应               │ ✓
```

**执行次数统计**:
- Filter前置: 3次 (1→2→3)
- Filter后置: 3次 (3→2→1)
- Interceptor preHandle: 3次 (1→2→3)
- Interceptor postHandle: 3次 (3→2→1)
- Interceptor afterCompletion: 3次 (3→2→1)
- Controller: 1次

### 场景2: SecondFilter 抛出异常

```
时间线    组件                      动作                      状态
───────┼────────────────────┼───────────────────────┼─────────
  1    │ FirstFilter        │ 前置处理               │ ✓
  2    │ SecondFilter       │ 前置处理               │ ✓
  3    │ SecondFilter       │ 抛出异常！             │ ✗ 异常
  4    │ FirstFilter        │ catch捕获异常          │ ✓ 异常处理
  5    │ FirstFilter        │ 写入错误响应           │ ✓
  6    │ 客户端             │ 收到500错误响应        │ ✓
───────┴────────────────────┴───────────────────────┴─────────
       以下组件不会执行：
       × SecondFilter 后置处理
       × ThirdFilter (完全不执行)
       × DispatcherServlet (完全不执行)
       × 所有 Interceptor (完全不执行)
       × Controller (完全不执行)
       × FirstFilter 后置处理 (因为在catch块中处理了)
```

**执行次数统计**:
- Filter前置: 2次 (1→2，第2个抛异常)
- Filter后置: 0次
- Interceptor preHandle: 0次
- Interceptor postHandle: 0次
- Interceptor afterCompletion: 0次
- Controller: 0次

**关键点**:
1. Filter异常在FirstFilter的catch块中捕获
2. 响应直接在catch块中处理，不再继续执行
3. Filter链完全中断，DispatcherServlet不会被调用
4. 这是Filter异常处理的"短路"特性

### 场景3: SecondInterceptor 抛出异常

```
时间线    组件                      动作                      状态
───────┼────────────────────┼───────────────────────┼─────────
  1    │ FirstFilter        │ 前置处理               │ ✓
  2    │ SecondFilter       │ 前置处理               │ ✓
  3    │ ThirdFilter        │ 前置处理               │ ✓
  4    │ DispatcherServlet  │ 接收请求，查找Handler   │ ✓
  5    │ FirstInterceptor   │ preHandle()            │ ✓ 返回true
  6    │ SecondInterceptor  │ preHandle()            │ ✓ 进入方法
  7    │ SecondInterceptor  │ 抛出异常！             │ ✗ 异常
  8    │ DispatcherServlet  │ 捕获异常               │ ✓ 异常处理
  9    │ FirstInterceptor   │ afterCompletion(ex)    │ ✓ 携带异常信息
 10    │ DispatcherServlet  │ 返回响应               │ ✓
 11    │ ThirdFilter        │ 后置处理               │ ✓
 12    │ SecondFilter       │ 后置处理               │ ✓
 13    │ FirstFilter        │ 后置处理               │ ✓
 14    │ 客户端             │ 收到响应               │ ✓
───────┴────────────────────┴───────────────────────┴─────────
       以下组件不会执行：
       × ThirdInterceptor preHandle (后续拦截器)
       × 所有 Interceptor 的 postHandle (因为Controller未执行)
       × Controller (未到达)
       × SecondInterceptor afterCompletion (未完成preHandle)
       × ThirdInterceptor afterCompletion (未执行preHandle)
```

**执行次数统计**:
- Filter前置: 3次 (全部执行)
- Filter后置: 3次 (全部执行)
- Interceptor preHandle: 2次 (1执行成功，2抛异常)
- Interceptor postHandle: 0次 (Controller未执行)
- Interceptor afterCompletion: 1次 (仅FirstInterceptor，因为只有它成功执行了preHandle)
- Controller: 0次

**关键点**:
1. Interceptor异常不会影响Filter的执行
2. 只有成功执行preHandle的Interceptor，其afterCompletion才会被调用
3. afterCompletion会接收到异常对象（ex != null）
4. Filter的后置处理仍然正常执行（洋葱模型完整）

## 三、异常处理机制对比

### Filter异常处理特点

```java
@Override
public void doFilter(ServletRequest request, ServletResponse response, 
                     FilterChain chain) throws IOException, ServletException {
    System.out.println("前置处理");
    
    try {
        chain.doFilter(request, response);  // 调用下一个Filter或DispatcherServlet
        System.out.println("后置处理");      // 如果上面抛异常，这里不执行
    } catch (Exception e) {
        System.out.println("捕获异常: " + e.getMessage());
        // 可以自定义错误响应
        response.getWriter().write("错误信息");
        // 不再向上抛出，请求处理结束
    }
}
```

**特点**:
- 必须显式try-catch，否则异常会向上传播到Servlet容器
- 捕获异常后可以自定义响应
- 后置处理代码不会执行（除非在finally中）
- 适合做安全过滤和错误拦截

### Interceptor异常处理特点

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, 
                         Object handler) throws Exception {
    System.out.println("preHandle执行");
    // 可以直接抛异常，Spring会处理
    if (条件) {
        throw new Exception("业务异常");
    }
    return true;
}

@Override
public void afterCompletion(HttpServletRequest request, HttpServletResponse response, 
                           Object handler, Exception ex) throws Exception {
    if (ex != null) {
        System.out.println("检测到异常: " + ex.getMessage());
        // 可以进行日志记录、资源清理等
    }
}
```

**特点**:
- 不需要try-catch，Spring会自动处理
- afterCompletion总是会执行（对于已执行preHandle的拦截器）
- afterCompletion可以获取异常对象进行处理
- 适合做业务逻辑校验和资源清理

## 四、调用栈分析

### 正常情况的调用栈

```
Thread: http-nio-8080-exec-1
  at Controller.test()
  at ThirdInterceptor.preHandle()
  at SecondInterceptor.preHandle()
  at FirstInterceptor.preHandle()
  at DispatcherServlet.doDispatch()
  at DispatcherServlet.doService()
  at ThirdFilter.doFilter()
  at SecondFilter.doFilter()
  at FirstFilter.doFilter()
  at ApplicationFilterChain.doFilter()
  at StandardWrapperValve.invoke()
  at StandardContextValve.invoke()
  at StandardEngineValve.invoke()
  at CoyoteAdapter.service()
  at Http11Processor.service()
  at AbstractProcessorLight.process()
  at SocketProcessorBase.run()
  at ThreadPoolExecutor.runWorker()
  at ThreadPoolExecutor$Worker.run()
  at TaskThread$WrappingRunnable.run()
  at Thread.run()
```

可以看到：
1. 最底层是Tomcat的线程池
2. 中间是Servlet容器的各个Valve
3. 然后是Filter链
4. 再是DispatcherServlet
5. 接着是Interceptor链
6. 最后是Controller

### Filter异常时的调用栈

```
Thread: http-nio-8080-exec-1
  at SecondFilter.doFilter()  ← 异常抛出点
  at FirstFilter.doFilter()   ← 异常捕获点
  at ApplicationFilterChain.doFilter()
  ... (Tomcat层)
```

异常在FirstFilter被捕获，不会继续向上传播。

### Interceptor异常时的调用栈

```
Thread: http-nio-8080-exec-1
  at SecondInterceptor.preHandle()  ← 异常抛出点
  at DispatcherServlet.doDispatch() ← 异常捕获点
  at ThirdFilter.doFilter()
  at SecondFilter.doFilter()
  at FirstFilter.doFilter()
  ... (Tomcat层)
```

异常在DispatcherServlet被捕获，然后触发afterCompletion调用。

## 五、实际应用场景建议

### Filter适用场景

1. **编码处理**
   ```java
   // 设置请求和响应的字符编码
   request.setCharacterEncoding("UTF-8");
   response.setCharacterEncoding("UTF-8");
   ```

2. **跨域处理（CORS）**
   ```java
   response.setHeader("Access-Control-Allow-Origin", "*");
   response.setHeader("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE");
   ```

3. **安全过滤**
   ```java
   // XSS攻击防护
   // SQL注入防护
   // 请求参数过滤
   ```

4. **全局日志**
   ```java
   // 记录所有请求的访问日志
   // 记录响应时间
   ```

### Interceptor适用场景

1. **权限校验**
   ```java
   @Override
   public boolean preHandle(...) {
       // 检查用户是否登录
       // 检查用户是否有权限访问该资源
       return hasPermission;
   }
   ```

2. **日志记录**
   ```java
   @Override
   public void afterCompletion(..., Exception ex) {
       // 记录请求处理时间
       // 记录异常信息
       // 记录业务操作日志
   }
   ```

3. **事务处理**
   ```java
   @Override
   public boolean preHandle(...) {
       // 开启事务
   }
   
   @Override
   public void afterCompletion(...) {
       // 提交或回滚事务
   }
   ```

4. **数据预处理**
   ```java
   @Override
   public boolean preHandle(...) {
       // 解析Token
       // 设置ThreadLocal
       // 加载用户信息
   }
   ```

## 六、最佳实践总结

### Filter最佳实践

1. **异常处理要完善**
   ```java
   try {
       chain.doFilter(request, response);
   } catch (Exception e) {
       log.error("Filter异常", e);
       // 返回友好的错误信息
   }
   ```

2. **避免在Filter中做复杂业务逻辑**
   - Filter应该简单、快速
   - 复杂逻辑放到Interceptor或Controller

3. **注意Filter顺序**
   - 通过Order设置优先级
   - 编码Filter应该最先执行

### Interceptor最佳实践

1. **利用afterCompletion进行资源清理**
   ```java
   @Override
   public void afterCompletion(..., Exception ex) {
       // 清理ThreadLocal
       // 释放资源
       // 记录日志
   }
   ```

2. **preHandle返回false时要设置响应**
   ```java
   @Override
   public boolean preHandle(...) {
       if (!hasPermission) {
           response.setStatus(403);
           response.getWriter().write("无权限访问");
           return false;  // 拦截请求
       }
       return true;
   }
   ```

3. **善用多个Interceptor组合**
   - 每个Interceptor专注单一职责
   - 通过组合实现复杂功能

## 七、面试常见问题

### Q1: Filter和Interceptor的区别？

| 维度 | Filter | Interceptor |
|------|--------|-------------|
| 规范 | Servlet规范 | Spring框架 |
| 执行时机 | DispatcherServlet之前 | DispatcherServlet之后，Controller之前 |
| 依赖 | 依赖Servlet容器 | 依赖Spring容器 |
| 可访问 | ServletRequest/Response | HttpServletRequest/Response + Spring上下文 |
| 异常处理 | 需要显式捕获 | Spring自动处理 |
| 资源访问 | 不能直接访问Spring Bean | 可以注入Spring Bean |

### Q2: 为什么Interceptor异常时，Filter后置处理还会执行？

因为Filter的执行机制是"洋葱模型"：
```
FirstFilter.doFilter() {
    前置处理;
    SecondFilter.doFilter() {
        前置处理;
        ThirdFilter.doFilter() {
            前置处理;
            DispatcherServlet处理; // 这里抛异常
            后置处理;
        }
        后置处理;
    }
    后置处理;
}
```

即使DispatcherServlet内部抛异常，只要异常不向上传播（被处理了），Filter的后置代码仍会执行。

### Q3: Interceptor的afterCompletion为什么只有已执行preHandle的才会调用？

这是为了保证对称性和安全性：
- 如果preHandle没执行，说明拦截器没有做任何资源准备
- afterCompletion主要用于资源清理，没有准备资源就不需要清理
- 这样可以避免afterCompletion中出现空指针等问题

示例：
```
FirstInterceptor.preHandle() ✓  → afterCompletion() ✓ 会执行
SecondInterceptor.preHandle() ✗ → afterCompletion() ✗ 不会执行
ThirdInterceptor.preHandle() ✗  → afterCompletion() ✗ 不会执行
```

### Q4: 如何选择使用Filter还是Interceptor？

**选择Filter的场景**：
- 需要在Spring MVC之前执行（如编码、跨域）
- 需要拦截所有请求（包括静态资源）
- 不需要访问Spring容器中的Bean

**选择Interceptor的场景**：
- 需要访问Spring容器中的Bean
- 需要访问Controller方法信息
- 需要在Controller前后做处理（如权限、日志）
- 只需要拦截Controller请求

## 八、源码参考

### Filter执行源码（ApplicationFilterChain）

```java
public void doFilter(ServletRequest request, ServletResponse response)
    throws IOException, ServletException {
    
    if (pos < n) {
        ApplicationFilterConfig filterConfig = filters[pos++];
        Filter filter = filterConfig.getFilter();
        filter.doFilter(request, response, this);  // 调用下一个Filter
    } else {
        // 所有Filter执行完毕，调用Servlet（DispatcherServlet）
        servlet.service(request, response);
    }
}
```

### Interceptor执行源码（DispatcherServlet）

```java
protected void doDispatch(HttpServletRequest request, HttpServletResponse response) {
    try {
        HandlerExecutionChain mappedHandler = getHandler(request);
        
        // 执行所有Interceptor的preHandle
        if (!mappedHandler.applyPreHandle(request, response)) {
            return;  // 如果返回false，直接返回
        }
        
        // 执行Controller方法
        ModelAndView mv = ha.handle(request, response, handler);
        
        // 执行所有Interceptor的postHandle
        mappedHandler.applyPostHandle(request, response, mv);
        
    } catch (Exception ex) {
        // 发生异常
        triggerAfterCompletion(request, response, mappedHandler, ex);
    }
    
    // 最终都会执行afterCompletion
    triggerAfterCompletion(request, response, mappedHandler, null);
}
```

---

**总结**: 
- **Filter**是Servlet容器级别的，执行在最外层，适合做通用的请求处理
- **Interceptor**是Spring MVC级别的，执行在DispatcherServlet内部，适合做业务相关的处理
- **异常处理**：Filter需要显式捕获，Interceptor由Spring自动处理
- **执行顺序**：Filter → DispatcherServlet → Interceptor → Controller → Interceptor → Filter
